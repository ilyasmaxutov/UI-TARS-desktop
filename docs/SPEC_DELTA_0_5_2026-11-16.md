# Platform Studio · инкремент ТЗ 0.5 (проект, не релиз)

**Дата:** 2026-11-16. **Основание:** исходный Platform Studio 0.4, коммит `3967b46d7b2e0e4b47ef4bdae98b6c01c415f378`, предыдущая спецификация 3.1 и экспорт `result.json` (394 Telegram-сообщения, 2026-08-02…2026-11-16). **Статус:** требования и план приёмки; этот документ **не** означает реализацию новых возможностей. Исходные PF001–PF096 и F01–F46 не закрываются и не перенумеровываются.

## 0. Суть запроса и приоритет

Пользователь хочет **содержательно более инициативного исследовательского и кодингового агента**, а не только сокращения числа технических вызовов. Текущая нежелательная траектория: модель вызывает множество одиночных команд, многократно возвращается к их результатам, не определяет границы исследования и часто начинает чинить симптом, прежде чем выяснит первопричину. Особенно заметно при поиске причин ошибок, сравнении реализаций и исследовании незнакомого кода.

**Три разных уровня — три разных обязательства:**

1. **Исследовательская стратегия**: сформулировать вопрос, гипотезы и различающие проверки; выбрать дешёвые проверки с высоким информационным выигрышем; собрать факты в причинную картину; обнаружить контрдоказательства; уметь остановиться.
2. **Исполнение**: сформировать один пакет зависимых/параллельных локальных действий; вычислить промежуточные данные и отфильтровать их вне контекста модели; вернуть только сводку с адресуемыми оригиналами. Code Mode — лишь одна из реализаций этого уровня.
3. **Контроль качества и долговременная память**: сохранять оригинальную цель, версию плана, сырьевые материалы, хэши, результаты экспериментов, отрицательные результаты, решение пользователя и исполнимую следующую проверку. Новый диалог или новая модель продолжают с той же цели, а не пересоздают расследование.

**Оптимизировать**: долю задач с корректным и практически применимым результатом на единицу оплачиваемого модельного ресурса и времени. Количество команд само по себе — вспомогательная метрика; десять локальных `read` внутри одного полезного пакета могут быть лучше, чем одна малоинформативная модельная реплика. Сокращение расходов не может скрывать ухудшение точности, полноты или безопасности.

## 2. Архитектурное решение R01: один основной исполнитель и «исследовательская процедура»

Точка входа — уже существующая `Task + GoalRevision`. Для сложных запросов включается режим `investigation` (для простых — прямой инструмент/ответ). Режим не требует второго постоянно работающего LLM или фонового наблюдателя.

```
GoalRevision (неизменённая оригинальная формулировка)
   ↓ [heuristic preflight: сложность/риск/источники]
ResearchPlan — рабочий контракт вопроса, гипотез, покрытия и остановки
   ↓ [ProbePlanner: модель выбирает диагностические вопросы / проверки]
DiagnosticSweep — компиляция проверок в локальный пакет действий
   ↓ [existing local_batch, tools, captured logs, repo/search, MCP adapters]
ProbeResults + immutable EvidenceRefs (включая отрицательные результаты)
   ↓ [Evaluator: какие гипотезы опровергнуты/усилены/остались]
Findings / DecisionGate / next sweep OR final deliverable
   ↓ [persist checkpoint in existing task/session store]
Next turn / resumed session / user correction
```

План **не** означает генерацию десятков псевдозадач или бюрократический цикл «модель-планировщик → модель-критик → модель-суммаризатор» на каждом шаге. Предпочтительно одно основное модельное контекстное окно + прогрессивное раскрытие навыков/документов. Субагент с чистым контекстом допускается лишь когда нужна независимая контрпроверка, действительно изолированный контекст или безопасный параллелизм; делегирование должно показать добавочную пользу.

### R02. Различающие гипотезы — вместо механического поиска

До глубокого исследования агент определяет:
- точный результат и запретные допущения пользователя; тип фактов, при котором ответ считается достаточным;
- 2–5 **проверяемых** альтернативных объяснений (если задача допускает гипотезы), включая альтернативу очевидной причине;
- наблюдение, которое отличит альтернативы, цену/риск и вероятную диагностическую ценность;
- точки остановки (факт найден, гипотеза опровергнута, свидетельств недостаточно, исчерпан бюджет/нужен доступ).

План выполняется **сразу пакетом** разрешённых read-only проверок; после него одна содержательная переоценка. Не заставлять модель сначала делать `pwd`, затем `ls`, затем `rg`, затем `cat` отдельными циклами, когда эти операции можно спланировать и обработать в одном проходе.

Адаптивность важнее жёсткости: если первая проверка обнаружила неожиданное состояние, второй этап плана пересчитывается; нельзя слепо запускать все действия без учёта зависимости, необходимости подтверждения и неопределённого внешнего эффекта. Безопасные независимые чтения — параллельно; мутации — исключительно через существующий авторитетный outbox и политику.

### R03. Контракт данных (логический, не новые обязательные таблицы)

```ts
type Investigation = {
  id: string; taskId: string; goalRevision: number;
  originalGoal: string; status: 'planning'|'probing'|'evaluating'|'blocked'|'review'|'complete';
  planVersion: number; scope: string[]; stopRules: StopRule[];
  budget: {modelTurns?: number; wallSeconds?: number; externalActions?: number; outputUtf8Bytes?: number};
};
type Hypothesis = {
  id: string; investigationId: string; claim: string;
  predicts: string[]; counterEvidence?: string[];
  state: 'open'|'supported'|'weakened'|'refuted'|'unresolved';
};
type Probe = {
  id: string; planVersion: number; question: string; discriminates: string[];
  operations: Array<{kind: string; params: unknown; dependsOn?: string[]}>;
  effect: 'read-only'|'external'|'mutation';
  priority: number; expectedInformation: string; acceptance: string;
};
type EvidenceRef = {
  id: string; kind: 'file-span'|'log-span'|'test-run'|'external-source'|'observation';
  locator: string; hashOrVersion?: string; observedAt: string;
  coverage: 'complete'|'partial'|'unknown';
};
type Finding = {
  id: string; assertion: string; evidenceIds: string[]; counterEvidenceIds: string[];
  kind: 'observed'|'inferred'|'hypothesis'; nextCheck?: string;
};
type SweepReport = {
  investigationId: string; probeIds: string[]; evidenceIds: string[];
  findings: Finding[]; untestedHypotheses: string[]; blockers: string[];
  nextAction: string; remainingBudget: unknown;
};
```

Реальные данные хранятся с версиями внутри действующих хранилищ, а не передаются целыми по контексту. Не сохранять в явном тексте ключи, персональные и системные секреты. Потребность в schema v4 обосновать проверенными контрактами; не добавлять таблицы без цели и миграционного теста.

### R04. Функция `diagnostic_sweep` как **надстройка** к `local_batch`

Вход: `investigationId`, `planVersion`, `probes`, `sourceSnapshot`, `limits`, `permissionScope`.

Выход: `sweepId`, `sourceHash`, массив статусов проверок, `evidenceRefs`, минимальный `summary`, `truncation/gaps`, `nextSuggestedQuestions` (если определены детерминированно), `unknownEffects`. Не выдавать модельную уверенность как факт.

Работа:
1. `preflight`: валидировать цели, разрешения, циклы зависимостей, точное ограничение вывода, запрет повторного side effect.
2. Скомпилировать чтения/поиски/сбор диагностик в существующий `local_batch`; результаты передавать следующим инструментам по сохранённым ссылкам, а не перепечатывать в промпт.
3. Искать локально по индексу и диапазонам, проверять SHA/версии. Пакетный read-only `rg`, метаданные, лог-срезы и фиксации Git не создают «отдельных модельных ходов».
4. Сохранить полный сырой результат в журнале, модель увидит компактный `SweepReport` с 1–3 релевантными фрагментами и ссылками на дополнительные. При ошибке/большом логе возвращать статус и адресуемый фрагмент, не молча удалять данные.
5. После результата агент принимает **одно содержательное** решение: устранить конкретную обнаруженную причину, заказать различающую проверку либо честно остановиться.

Существующая Go 0.4 не является универсальным JS-runtime; её `local_batch` выполняет фиксированные операции. Не выдавать `diagnostic_sweep` за реализованный Code Mode до написания и проверки соответствующей функции.

### R05. Code Mode — сменяемый адаптер, не системная зависимость

`DirectTools | LocalBatch | CodeMode`: три интерфейса выполнения одного плана. По умолчанию — уже доступные операции 0.4. Если установленный Codex действительно поддерживает `code_mode`, выполнить compatibility probe в изолированной тестовой сессии, затем использовать JS-host **как опциональный бэкенд**. Пока реестр Codex показывает `code_mode` в `UnderDevelopment` (выключен), не ставить его в обязательный путь.

Claude Code Code Mode — экспериментальный терминальный режим v2.1.323+, `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`; его механизм: JS объединяет инструменты, параллельные вызовы, фильтрацию ответов. Документация указывает ограничения по возобновлению и средам. Публикация Anthropic 2025-11-04 про MCP — пример экономии на **передаче описаний и промежуточных результатов**, а не универсальное доказательство улучшения качества рассуждений.

**Непреодолимая пока граница:** если обычный Codex свободно вызывает собственный shell независимо от Studio MCP, Studio не сможет *гарантировать*, что он не сделает десятки одиночных команд. Сначала можно дать skill/AGENTS.md-правило и предпочтительный batched tool, затем сравнить реальные traces. Жёсткое принуждение требует документированного контролируемого маршрута всех инструментов; не создавать хрупкий неофициальный перехват внутренних RPC.

### R06. Наблюдаемость без «чтения мыслей»

Показывать пользователю не сырые бессистемные «тулколлы», а **ход исследования**: поставленный вопрос, задействованные файлы/версии, альтернативы, проверка, результат, что ещё неизвестно, стоимость. Продвинутый режим разворачивает команды и raw evidence. Доступные host/provider events — наблюдения, а не скрытое внутреннее рассуждение модели.

`span` / `event` атрибуты: `taskId`, `goalRevision`, `investigationId`, `sweepId`, `probeId`, `sessionId`, `externalCommandId`, `sourceHash`, `status`, `duration`, `observedTokens` (если источник действительно возвращает), `bytesToModel`, `error`, `resumed`, `truncated`, `gap`. Сброс/переход между сессиями не теряет цепочку происхождения.

### R07. Накопление навыков и смена стратегии

Из завершённого **проверенного** расследования извлекать короткую переиспользуемую запись:
- «как здесь собирать/тестировать», точная команда, тип среды, версия зависимостей, результат прогона;
- повторяемые причины ошибок и **когда эта диагностика неприменима**;
- заблокированные подходы/ошибочные действия;
- полезный диагностический шаблон `problem-pattern → sweep → acceptance`.

Новое знание — кандидат, не автоматический закон. Промпт/скилл изменения хранить отдельно, с diff, областью применимости и возможностью отката. Автоматическая эволюция конфигурации или инструмента — только после A/B с отложенными кейсами, ревью безопасности и согласия пользователя на расширение прав. Не переименовывать произвольную модельную память в постоянную истину.

### R08. Состояния прерывания и остановки

При `interrupt`, `timeout`, смене модели или конце квоты сохраняются: точная цель, последняя версия плана, уже исполненные safe probes, их `EvidenceRef`, незавершённые/unknown операции, следующий разрешённый шаг. Read-only сверка предшествует возобновлению. Команду с возможным внешним эффектом нельзя повторить с новым id, чтобы «разблокировать» зависание. Watchdog останавливает циклы без прироста информации, но не уничтожает полезные долгие операции.

**Выполнение важнее бесконечного планирования:** когда решение установлено, агент обязан переходить к исправлению/доставляемому артефакту и его приёмке; не добавлять новые циклы ради анализа.

### Негативные кейсы в приёмке

- 100 МиБ логов с найденным совпадением в середине; ни полный лог, ни prompt tools.schemas не сериализуются в модельное окно.
- Неверный root, символическая ссылка / junction, неполное чтение, изменившаяся версия файла → trace сообщает несоответствие, не уверенный вывод.
- Потеря ACK после принятия внешней команды → read-only reconcile, без новой мутации.
- Две гипотезы, которые объясняют один симптом, но требуют разных исправлений → запрашивается отличающая проверка.
- Несколько одинаковых ошибок команды → сохраняется диагностика и смена подхода, не бесконечный retry.
- Независимый критик нашёл контрпример → обновляется версия вывода, не маскируется первоначальная уверенность.
- Простой запрос «показать строку» → никаких дорогих гипотез и дополнительного LLM.
- Отсутствие Code Mode и сети → рабочий базовый сценарий `local_batch`.
- Пользователь меняет цель посреди исполнения → новая GoalRevision, старый evidence остаётся привязан к оригиналу.

## 5. Пример критического сценария: «Почему сессия Codex зависает после resume?»

**Плохо:** модель последовательно вызывает `pwd`, `ls`, `cat`, `grep`, видит кусок лога, меняет конфиг, повторяет и спустя 25 ходов сообщает «попробуйте переустановить».

**Требуемое:** один `ResearchPlan` с гипотезами «модель/провайдер», «App Server transport», «потерянный ACK», «данные Store», «неправильный ABI/schema». Один `diagnostic_sweep` собирает версии CLI, конфиг из разрешённого профиля без секретов, read-only события host, последние статусы outbox, результаты поиска строк ошибок, локальные хэши. Модель видит таблицу наблюдений по времени и **различающий тест**. Только после этого предлагает конкретное исправление и проверяет прежний/новый сценарий. Если Codex недоступен, выдаёт точный неизвестный блокер, а не заменяет живой запуск фикстурой.

## 6. Правила изменения проекта

- Продолжать **именно** ветку/снимок 0.4 (`3967b46…`); на GitHub `ilyasmaxutov/UI-TARS-desktop` в `main` пока **старый форк UI-TARS**, поэтому не считать его источником версии 0.4 без явной миграции и сверки.
- Не заменять Rust/Tauri, native Store, существующий Desk, `local_batch` и визуальный Canvas ещё одной системой. Идеи внешних проектов заимствовать адресно; не клонировать их окружения ради модных функций.
- Объём нового кода сначала ограничить проверяемой read-only диагностикой. Любые изменения полномочий, внешние действия, запуск платных моделей и автопродолжение — отдельно авторизованные механизмы.
- В каждом отчёте отделять `implemented`, `locally tested`, `Windows validated`, `live Codex verified`, `product accepted`. Нельзя по числу unit-тестов закрывать PF целиком.
- Сначала выполнить **реальную работу и тест**, потом обновить статус. Вся дальнейшая разработка должна измерять реальную полезность исследования, а не количество добавленных агентов/скиллов.
